# ADR-0008: PWA basics via `vite-plugin-pwa` (`generateSW`), app-shell-only scope

## Status

Accepted

## Context

[Phase 4 roadmap](../roadmap/phase-4-offline-pwa.md) groups two quite different pieces of work
under one phase: "Lokale Datenhaltung"/"Synchronisation" (IndexedDB, optimistic UI, a sync queue,
last-write-wins conflict resolution) and "PWA" (Web App Manifest, a service worker for app-shell
caching, installability). This decision covers **only the "PWA" checklist items** — a deliberately
narrowed first slice ("PWA basics"). Offline data capture, the sync queue, conflict resolution, and
the three offline-data test scenarios are an explicitly separate, later slice and remain
unimplemented; nothing in this ADR should be read as covering them.

Two design questions needed deciding:

1. Hand-roll a manifest file and a service worker, or use a build-tool plugin that generates them?
2. Where does service worker *registration* happen — auto-injected by a plugin, or explicit app
   code — and does that registration run from React lifecycle code or plain module-scope code?

Constraints already established elsewhere in the codebase that shaped this:

- The frontend is a Vite-built SPA; the single-container deployment already copies the entire
  frontend build output into `apps/backend/dist/public`, and `ServeStaticModule` serves everything
  there except `/api` and `/health` (see root `CLAUDE.md`). Any static file that ends up in the
  frontend's `dist/` is therefore already served in production with zero backend changes.
- `config.yml`/`apps/backend/src/config` carry zero branding-related fields (confirmed by
  inspection) — there is no existing "app name"/"theme color" concept anywhere in the backend
  config system to hook into.
- There is no design system yet (that's [Phase 6](../roadmap/phase-6-design-system-ux.md)) — any
  visual choice made here (icon, color) is necessarily a placeholder.

## Decision

### a) `vite-plugin-pwa` with the `generateSW` strategy, not a hand-rolled manifest/service worker

Chose the `vite-plugin-pwa` devDependency (using its default `generateSW` strategy, backed by
Workbox) over writing `public/manifest.webmanifest` and a service worker script by hand.

- `generateSW` derives the precache manifest (which built asset URLs to cache, with
  content hashes for cache-busting) directly from Vite's own build output, so the cached asset list
  can never drift out of sync with what a given build actually produced — a hand-rolled service
  worker would need its own logic to enumerate and hash `dist/assets/*` on every build.
  `cleanupOutdatedCaches: true` additionally lets Workbox prune a previous build's now-unused
  precache entries on activate, which a hand-rolled worker would also have to reimplement.
- The manifest is written once, as a plain object (`pwa.config.ts`), and the plugin serializes it to
  `manifest.webmanifest` at build time — no hand-written JSON file to keep in sync with the plugin's
  own expectations (e.g. icon `purpose` values) needed.
- Tradeoff accepted: an additional devDependency (and `workbox-build`/`workbox-window` as its
  transitive peers) versus zero new dependencies for a hand-rolled approach. Judged worth it — the
  precache/cache-busting correctness `generateSW` provides for free is exactly the kind of logic
  that's easy to get subtly wrong by hand and hard to notice when it's wrong (a stale cached asset
  silently served instead of a new one).

### b) Manifest and icons are static, build-time content — not `config.yml`-driven

`pwa.config.ts` exports a plain, hard-coded manifest object (name, short name, colors, icons); none
of it is read from `config.yml` or any backend endpoint. This mirrors decision context point 2
above: no branding concept exists anywhere in this app's config system today, and inventing one
for a placeholder icon/color pair (see decision (d)) would be speculative, not-yet-justified scope.
If a future phase (e.g. Phase 6's design system, or a rebrand) introduces real per-deployment
branding, the manifest would need to move to being generated by the backend or injected via an
env-driven build step at that point — not before it's actually needed.

### c) Registration is explicit app code, not the plugin's auto-injected register script

`vite-plugin-pwa` can auto-inject a small script that calls the generated `virtual:pwa-register`
module for you (`injectRegister: 'auto'`/`'script'`). This was turned off
(`injectRegister: false`) in favor of a small dedicated function,
`registerServiceWorker()` (`apps/frontend/src/pwa/registerServiceWorker.ts`), called once from
`main.tsx` at module scope — not from a React `useEffect`.

Reasoning:

- Module-scope placement means registration runs exactly once per page load, independent of React
  StrictMode's deliberate double-invocation of effects in development (which would otherwise call
  `.register()` twice per mount in dev, harmless in practice since a second `register()` call for
  the same URL is a no-op, but still not the semantics this decision wants to depend on).
  Registration has no relationship to any component's mount/unmount lifecycle — it belongs with the
  other one-time startup wiring already at the top of `main.tsx` (`./i18n` side-effect import,
  `queryClient` construction).
- `registerType: 'prompt'` (rather than `'autoUpdate'`) was chosen to match this manual-registration
  posture: `'autoUpdate'` has Workbox skip-waiting/claim clients automatically the moment a new
  service worker is installed, which fits an auto-injected, always-on-latest-version registration
  flow; `'prompt'` leaves that activation step to whatever explicitly calls
  `postMessage({ type: 'SKIP_WAITING' })` — consistent with keeping registration (and any future
  update-prompt UI) deliberately explicit rather than implicit plugin behavior.
- `registerServiceWorker()` is a no-op outside of a production build (`import.meta.env.PROD` false)
  since `vite dev` never emits `/sw.js`, and a no-op when `navigator.serviceWorker` isn't supported
  (older/non-supporting browsers) — feature-detected rather than assumed. A registration failure is
  logged via `console.error`, not thrown, since the app must stay fully usable without a service
  worker; this slice only adds offline *app-shell* caching, nothing the app depends on functionally.

### d) Manifest colors and icon are a placeholder, not a design decision

`theme_color: '#1e293b'` / `background_color: '#0f172a'` (a neutral dark slate pair) and a plain
"B"-on-solid-background SVG icon (`apps/frontend/public/icons/app-icon.svg`, rasterized to the PNG
sizes the manifest/`apple-touch-icon` need) are explicitly placeholders, not real branding — there
is no design system yet (Phase 6). The same `theme_color` value is duplicated in
`index.html`'s `<meta name="theme-color">` tag (the manifest's `theme_color` only affects the
browser's own installed-app chrome, not the tab/address-bar color of the page itself before
installation, so both need to agree independently). Icon content is kept within a centered ~80%
"safe zone" so the same source works for both regular (`purpose: 'any'`) and maskable
(`purpose: 'maskable'`) icon variants without being clipped when a platform applies a circular/
rounded mask — see the SVG's own doc comment.

### e) API and Socket.IO traffic are deliberately excluded from all service worker caching

`workbox.navigateFallbackDenylist` excludes `/api/` and `/health` from the SPA-fallback
navigation route, and — just as importantly — no `runtimeCaching` entries were added for `/api/**`
at all. This means every API request (including the Socket.IO handshake, which also lives under
`/api` per [ADR-0007](0007-websocket-realtime-sync.md)'s addendum) is untouched by the service
worker and goes straight to the network, exactly as if no service worker were installed. This is a
direct consequence of this slice's scope boundary (decision below) rather than an oversight: caching
or replaying API responses is offline-*data* behavior, which is explicitly out of scope here.

### Scope boundary: installable app shell with offline app-shell caching only — not offline data capture

This slice's Definition of Done is narrowly "the app is installable (manifest + service worker
exist, home-screen icon, standalone window) and its static shell can be served from cache when
offline" — **not** "new entries can be logged offline," which is the separate, later slice
described by this phase's "Lokale Datenhaltung"/"Synchronisation" checklist items (IndexedDB layer,
optimistic UI, sync queue, last-write-wins conflict resolution) and its three test scenarios. None
of that is touched, implemented, or assumed by this ADR. A user who opens the app while offline will
see the last-cached shell render, but any data-fetching/mutating request still requires
connectivity, since decision (e) means the service worker never intercepts or answers on its own.

Real device/browser installability (Android/iOS/Desktop home-screen install flow) was **not**
manually verified as part of this slice — only automated build/manifest/service-worker checks were
run (see [Phase 4 roadmap](../roadmap/phase-4-offline-pwa.md)'s note under "Installierbarkeit
testen"). That manual verification remains outstanding.

### Migration path if a later slice needs more control than `generateSW` gives

`generateSW` computes and owns the entire service worker file; there's no hook to add hand-written
runtime logic (e.g. a background-sync event listener draining an offline sync queue) inside it. If a
later slice (most plausibly the offline-data slice itself, if it decides an actual service-worker
`sync` event is the right retry mechanism rather than an in-page retry loop) needs that, the
established migration path is switching `vite-plugin-pwa`'s `strategies` option from `generateSW` to
`injectManifest` — which still generates and injects the precache manifest constant into a
service-worker source file you write yourself, keeping the precache-correctness benefit from
decision (a) while allowing arbitrary custom logic alongside it. This is a documented, supported
mode of the same already-chosen dependency, not a rewrite.

## Consequences

**Positive:**

- The precache manifest (`dist/sw.js`'s list of hashed asset URLs) is mechanically derived from the
  real Vite build output on every build, so it can't silently drift from what was actually built.
- No backend or Docker changes were needed at all — the existing "copy the whole frontend `dist/`
  into `apps/backend/dist/public`, serve everything except `/api`/`/health`" pipeline already serves
  `manifest.webmanifest`, `sw.js`, and the icon files the moment they exist in `dist/`.
- Explicit, module-scope registration (decision (c)) means service-worker lifecycle behavior is
  visible, ordinary application code (testable with a plain unit test,
  `apps/frontend/src/pwa/registerServiceWorker.spec.ts`), not something implicitly wired in by a
  build plugin.
- The `injectManifest` migration path (see above) means choosing `generateSW` now doesn't foreclose
  custom service-worker logic later, if the offline-data slice ends up needing it.

**Negative / tradeoffs:**

- A new devDependency (`vite-plugin-pwa`, pulling in `workbox-build`/`workbox-window`) was accepted
  in exchange for not hand-rolling precache/cache-busting logic — judged worth it per decision (a).
- The manifest's visual identity (icon, colors) is a placeholder that will need real design-system
  work later (Phase 6) — this was accepted deliberately (decision (d)) rather than blocking this
  slice on a design decision that has no owner yet.
- No manual real-device installability testing was performed (see the scope-boundary section above)
  — the roadmap file carries an explicit outstanding note for this, so it isn't silently dropped.
