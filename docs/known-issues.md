# Known Issues / Follow-up TODOs

Small, non-blocking items deliberately deferred during implementation. Not scheduled to a specific roadmap phase — revisit when finishing up / hardening before a release.

- **Flaky backend e2e tests (occasional `socket hang up`)**: observed intermittently (~1 in 6 runs as of Phase 1, sub-step 3) across `apps/backend/test/*.e2e-spec.ts`. Root cause: the Nest test app in these specs is never bound to a real HTTP port (no explicit `app.listen()`/`.getHttpServer()` setup with a listener), which `supertest` tolerates most of the time but occasionally races under concurrent requests. First noticed during Phase 1 sub-step 2's review (attempting true HTTP-level concurrency tests for the invite-accept race also hit `ECONNRESET` for the same reason). Fix direction: bind the test app to an ephemeral port in `beforeAll` (`await app.listen(0)`) instead of relying on `app.getHttpServer()` alone. Not a correctness bug in application code — purely a test-harness reliability issue.
- **Undifferentiated 400 errors on child create/update**: the backend returns free-text `400` messages for both DTO validation (name/birthDate) and photo constraint violations (Multer/`ParseFilePipeBuilder`), with no machine-readable error code. The frontend (`apps/frontend/src/child/mapChildError.ts`) therefore collapses all child-create/update `400`s to one generic translated message rather than a field-specific one — client-side pre-validation already catches the common cases (future birth date, wrong photo type/size), so the residual server-side `400`s are narrow edge cases (clock skew, content-sniffing mismatch). Noted during Phase 1's household/child management UI sub-step as a deliberate simplification; revisit if/when the backend exposes structured validation error codes (candidate for v2 hardening, see `docs/roadmap/phase-7-v2-erweiterungen.md`).
- **No shared UI primitives / design system layer**: `apps/frontend/src/components` currently holds only feature-coupled components (`AuthForm`, `FeedingEventForm`, `ChildForm`, etc.) tied to domain logic, data-fetching and routing; there is no reusable, generic primitives layer (Button, TextField, Select, Card, Dialog, Badge, Spinner) with design tokens (color/spacing/typography) — confirmed by the `// no UI kit in this project yet` comments in `ErrorMessage.tsx`/`LoadingIndicator.tsx`, and only `apps/frontend/src/styles/breakpoints.css` exists for styling. This blocks using Claude Design's `/design-sync` skill productively (it needs a real component library — ideally with Storybook — to sync; business components don't translate into reusable design-system building blocks). Candidate next step: extract a `apps/frontend/src/components/ui/` primitives layer with design tokens, add Storybook scoped to it, then run `/design-sync`. Raised 2026-08-02 during a Claude Design walkthrough; not scheduled to a specific roadmap phase. **Largely resolved (2026-08-16) by Phase 6 M1**: the `apps/frontend/src/components/ui/` primitives layer, design tokens (`design-system/tokens/*.json` → generated `tokens.generated.css`), and a scoped Storybook catalog now exist (see [ADR-0013](adr/0013-design-system-styling-approach.md) and `docs/design-system/`). Only the actual `/design-sync` push to a claude.ai design-system project remains outstanding, plus the separate M2/M3 work of migrating existing feature screens onto the primitives.
- **No service worker update-prompt UI**: `apps/frontend/src/pwa/registerServiceWorker.ts` registers the service worker (`registerType: 'prompt'`, see [ADR-0008](adr/0008-pwa-basics-via-vite-plugin-pwa.md) decision (c)) but never listens for an updated worker or posts `{ type: 'SKIP_WAITING' }`, and there is no update-prompt UI. Consequence: after every redeploy, a new service worker installs but sits in the "waiting" state until a user fully closes all tabs/windows for the origin, so installed/PWA users keep running the previously cached app shell until then. Deliberately deferred per ADR-0008; revisit if frequent redeploys are expected before the offline-data slice (Phase 4's "Lokale Datenhaltung"/"Synchronisation") lands. Raised 2026-08-03 during review of the PWA basics slice.
- **Manual PWA installability verification not yet performed**: Phase 4's "Installierbarkeit testen (Android/iOS/Desktop-Browser)" item requires actually installing the app from a real Android/iOS/Desktop browser and confirming the homescreen icon + standalone window behave correctly — something that can't be verified by an automated agent. Automated checks (manifest/service-worker/icons build and are served correctly) are done; only the real-device/browser check is outstanding. All other Phase 4 items are complete. Revisit before a release, or whenever a device is available to test with. Raised 2026-08-15 when closing out Phase 4.
- **Capacitor wrapper — real-device Android build + install + launch not yet verified**: Phase 5 scaffolded the Capacitor wrapper (`apps/frontend/capacitor.config.ts`, committed `android/`/`ios/` projects, `cap:sync`/`cap:android`/`cap:ios` scripts — see [ADR-0012](adr/0012-capacitor-native-wrapper.md)) and confirmed the `cap sync` build pipeline runs, but actually building the Android app in Android Studio, installing it on a device/emulator, and launching it can't be done by an automated agent (no Android SDK/signing/device here — the same posture as the deferred PWA-installability item above and the deliberate "no native builds in CI" scope decision). Android is the primary target for the roadmap's "builds and installs on at least one platform" DoD item. Revisit when a device/emulator + Android Studio are available. Raised 2026-08-15 during Phase 5.
- **Capacitor wrapper — cookie/origin auth smoke test against a real non-localhost backend**: the session design (ADR-0001) uses httpOnly `SameSite=Lax` cookies with `credentials: 'same-origin'`, which assumes the frontend and backend share one origin. Inside a Capacitor WebView the web assets are served from a local scheme origin (`https://localhost` on Android with `androidScheme: 'https'`, `capacitor://localhost` on iOS), which differs from a remote backend's HTTPS origin, so cross-origin cookies may not be sent — silently breaking auth. `capacitor.config.ts` documents the two candidate fixes (point the WebView at the backend origin via `server.url`/`server.hostname`, vs. a backend CORS + `credentials: 'include'` + `SameSite=None` change); choosing and validating one needs a real device against a real non-localhost backend deployment. Outstanding manual verification. Raised 2026-08-15 during Phase 5.
- **Capacitor wrapper — offline IndexedDB sync smoke test inside the wrapped app**: the offline layer (Phase 4: IndexedDB optimistic create/edit, reconnect sync queue — ADR-0009/0010/0011) has automated tests in the browser/jsdom environment, but hasn't been exercised inside the Capacitor WebView. Verify the airplane-mode-create → reconnect → sync flow behaves the same on a real device. Raised 2026-08-15 during Phase 5.
- **Capacitor wrapper — background-suspension of the sync-queue retry timer**: `apps/frontend/src/offline/syncQueue.ts` reschedules retries via `setTimeout`; mobile OSes suspend JS timers while an app is backgrounded, so a pending retry may not fire until the app is foregrounded. Verify whether resuming the app reliably resumes retries, or whether `@capacitor/app`'s `appStateChange` event needs to be wired in to kick the queue on resume (a follow-up if so). Raised 2026-08-15 during Phase 5.
- **Push notification end-to-end delivery to a real device not verified**: Phase 5 implemented the full backend send path (`PushSenderService` wrapping `firebase-admin`, `NotificationSchedulerService` cron triggers) and frontend registration/settings, all covered by unit tests that mock `firebase-admin` (no real network/Firebase call is ever made in tests). Actually delivering a push to a physical device requires a real Firebase project + service-account credential (`push.firebase.serviceAccountPath` in `config.yml`) and a real device with the wrapped app installed — which can't be automated here. Outstanding manual verification: configure a real Firebase project, register a device token, and confirm both the feeding-reminder and daily-summary pushes arrive. Raised 2026-08-15 during Phase 5.
