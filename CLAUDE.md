Phase 6 Milestone M1 (design-system foundation) has been implemented — a pure frontend/presentation-layer slice that changes no data models, API contracts, or business logic, and deliberately migrates **no** existing screen onto the new system (that's the later M2/M3, still unchecked in the roadmap). Phase 7.1 (Wachstumstracking / growth tracking) has been implemented — the first post-MVP sub-phase and the first child-domain feature deliberately modelled *beside* `Event` rather than as an event type. Growth is **online-only**: it is wired into neither realtime ([ADR-0007](docs/adr/0007-websocket-realtime-sync.md)) nor the offline engine ([ADR-0009](docs/adr/0009-indexeddb-optimistic-create-engine.md)/[ADR-0010](docs/adr/0010-offline-sync-queue-reconnect-retry.md)/[ADR-0011](docs/adr/0011-offline-edit-stop-and-last-write-wins.md)); saving visibly fails offline with no faked success (W-16), and although `GrowthMeasurement.updatedAt` exists it is traceability/export-only — the ADR-0011 Last-Write-Wins path does not apply (the update DTO has no `clientTimestamp`). A standalone `GrowthMeasurement` table (FKs to `Child` + `User`; integer base units grams/millimetres — `weightGrams`/`lengthMillimeters`/`headCircumferenceMillimeters`, each individually optional under an application-level "at least one" rule; a `lengthMeasurementPosition` string override; `@@index([childId, measuredAt])`; `onDelete: Cascade` on the child relation only) plus one new optional `Child.sex` string column (`FEMALE`/`MALE`/null, read only through `toChildSex()` in `apps/backend/src/child/child-sex.enum.ts`) land in a single additive Prisma migration (`20260902001457_add_growth_measurement_and_child_sex`); the rationale is the new `GrowthMeasurement` addendum in [ADR-0006](docs/adr/0006-event-base-table-with-per-type-detail-tables.md). Backend module `apps/backend/src/growth/` (controller/service/DTOs, mirroring the feeding module; `HouseholdMembershipGuard` re-declared as a provider, no `@RequireRole` on any route — that audit is deliberately deferred to Phase 7.5) exposes routes under `households/:householdId/children/:childId/growth`: `POST`, `GET` (list, optional `from`/`to`), `GET /reference?indicator=`, `GET /:id`, `PATCH /:id`, `DELETE /:id` (204), on the same `JwtAuthGuard`/`HouseholdMembershipGuard`/`CsrfGuard` stack as the event controllers. WHO Child Growth Standards reference data is **vendored**: the igrowup LMS tables (`weianthro.txt`/`lenanthro.txt`/`hcanthro.txt`, columns sex/age-in-days/L/M/S) under `apps/backend/src/growth/reference-data/source/` are converted once by a Bun codegen script (`scripts/convert-who-tables.ts`) into generated `*.data.ts` modules; provenance and the **CC BY-NC-SA 3.0 IGO** licence (non-commercial / share-alike / attribution — consistent with the self-hosted-only, no-SaaS principle) are documented in `apps/backend/src/growth/reference-data/README.md` and in each module's `PROVENANCE` const. The reference range is 0–1826 days (5×365.25, floored); recumbent length-for-age vs standing height-for-age split at day 731 via the source file's own `loh` flag. Percentiles/z-scores are computed **on every read and never persisted** (they depend on the mutable `Child.sex` and on the age-derived reference choice, which per W-18 is not frozen at creation) by the pure, dependency-free `apps/backend/src/growth/percentiles/` — `standard-normal.ts` (Φ via the Zelen & Severo / A&S 26.2.17 approximation), `growth-percentiles.ts` (`z = ((X/M)^L−1)/(L·S)`, or `ln(X/M)/S` for `L≈0`; nearest-grid-point lookup, no interpolation), `age-in-days.ts` — tested against the vendored tables' own z-score columns. The body-measure reference is auto-selected from age at measurement time (W-17), overridable per measurement via `lengthMeasurementPosition` (W-18); when the override contradicts the age-derived choice the value is corrected by the standard WHO ±7 mm recumbent↔standing adjustment (`LENGTH_HEIGHT_ADJUSTMENT_MM`) before scoring, while the *displayed* method still reflects the user's choice (W-19), and the `GET .../growth/reference` bands are served unadjusted. Missing `Child.sex` → measurements and trend still render but no percentiles, with an explanatory hint linking to the child profile (`CHILD_SEX_NOT_SET`, W-10 — no guessed default); age outside 0–1826 d (including a negative age after a birth-date correction) → `UNAVAILABLE` with `AGE_ABOVE_REFERENCE_RANGE`/`AGE_BELOW_REFERENCE_RANGE`, trend without bands plus a hint (W-11). `measuredAt` is stored as a bare calendar day (`YYYY-MM-DD`, mirroring `Child.birthDate`) via a new `@IsDateOnly()` validator in `apps/backend/src/common/validators/`; `IsNotFutureDate` gained a date-only branch (with a max-UTC-offset tolerance) that also fixes the same latent timezone bug for `birthDate`. The raw-data export (`apps/backend/src/export/`) gained a `recordKind` discriminator (`'EVENT'`/`'GROWTH_MEASUREMENT'`) plus growth value/percentile/z-score columns, all appended **after** the existing `RawExportRow`/CSV-header columns so positional consumers are unaffected; growth rows are merged and chronologically sorted with events, percentiles rounded to whole numbers and z-scores to 2 decimals. Frontend: new routes `households/:householdId/children/:childId/growth` (+ `/growth/new`, `/growth/:measurementId/edit`) in `App.tsx` with a `TrendingUp` nav item in `Layout.tsx`; `apps/frontend/src/api/growth-api.ts` is online-only (no `src/offline/` imports, no `clientTimestamp`), `lib/growthUnits.ts` does kg↔g / cm↔mm with one-directional integer rounding (no float storage, W-3) and `lib/growthMeasureVisuals.ts` maps each measure to field/color/icon. The chart is **visx**, loaded as a `React.lazy` async chunk (~26 kB gzip, **0 kB** added to the initial bundle) — see the new [ADR-0014](docs/adr/0014-charting-library-visx.md); `components/growth/GrowthChart*` share one cursor hook (`useGrowthChartCursor`) driving pointer hover, touch long-press-and-scrub (`touch-action: none` only while scrubbing + pointer capture) and arrow-key navigation with an `aria-live` readout (W-13/W-14), percentile bands P3/P15/P50/P85/P97 as stacked areas (W-12), and deliberately no draw animation at all. Entry form and list build on the design-system primitives (`Card`/`Input`/`Select`/`Tabs`/`Textarea`); new color tokens `growth-weight`/`growth-length`/`growth-head-circumference`/`growth-band` in `design-system/tokens/color.json` (regenerated via `bun run design-tokens:build`), while `design-system/tokens/event-types.json` is deliberately untouched (growth is not an `EventType`). `ChildForm`/`ChildSettings`/`ChildCreate` gained the optional sex field with an explicit "not specified" option (omitted entirely on create, resets a previously-set value on edit), `ChildHome` gained a "Wachstum" summary card (W-15, `GrowthSummaryCard`), and a new `growth` i18n namespace plus `child.fields.sex*` keys exist in both de and en. No `components/ui/` primitive was added or changed, so Storybook was not rebuilt. ## Architecture (as decided in the PRD, not yet implemented)

- **Self-hosted only** — no SaaS/cloud offering. Deployment via Docker/Docker Compose. Configuration (including OIDC providers and DB provider) is done via a config file, not an admin UI.
- **Backend: NestJS** (deliberately chosen over Next.js — see PRD section 5.3 for the full comparison). Key reasons: native long-lived Node process for WebSockets (`@nestjs/websockets`), and a structured Guard/Passport-strategy model for running local auth and OIDC side by side.
- **Frontend: React + Vite** (SPA, no Next.js — this is an internal, logged-in family app with no SEO/SSR need). Mobile-first from the start.
- **Auth**: local email/password (Argon2 hashing) *and* OIDC (Authorization Code Flow + PKCE) coexist; users pick a method at login. One or more OIDC providers (Keycloak, Authentik, Google, Entra ID, …) are registered via config file, not code changes. Session/token handling (local auth, implemented in Phase 1): JWT access + refresh tokens in httpOnly, `SameSite=Lax` cookies, with DB-backed refresh-token rotation and reuse detection — see [ADR-0001](docs/adr/0001-jwt-httponly-cookie-session-handling.md) for the full rationale, since PRD 5.1 left this open. OIDC (not yet implemented) will reuse the same token/cookie infrastructure.
- **Data model** (see PRD 5.2): `User —< Membership >— Household —< Child —< Event`. Every `Event` (Feeding/Sleep/Diaper) references both the `Child` and the `User` who logged it. Authorization is checked via the user's `Membership` role in the `Household`. `Event` itself is a shared base table (`type`, `occurredAt`, `startedAt`/`endedAt` for timer-based types); type-specific fields live in a 1:1 detail table per event type, but only where a type actually has fields beyond what `Event` already carries — `FeedingDetail` implemented in Phase 2 (Stillen/Fläschchen/Beikost); Sleep (also implemented in Phase 2) turned out to need no detail table at all, since start/stop timer + backfill is fully covered by base-`Event` columns; `DiaperDetail` (implemented in Phase 2, the third and final MVP event type) does follow the `FeedingDetail` pattern, since Diaper has type-specific fields (`diaperType`, optional consistency note) — see [ADR-0006](docs/adr/0006-event-base-table-with-per-type-detail-tables.md) including its Sleep and Diaper addenda. All three MVP event types (Feeding/Sleep/Diaper) are now implemented, closing out Phase 2's "Tracking-Kernfunktionen".
- **Real-time sync**: implemented in Phase 3 slice 1 — a Socket.IO gateway (`RealtimeGateway`/`RealtimeService` in `apps/backend/src/realtime/`) attached to the same HTTP server as the REST API, consumed via `RealtimeProvider`/`useHouseholdRoom` in `apps/frontend/src/realtime/`. WS handshake auth reuses the same JWT/cookie infrastructure as HTTP through a newly extracted `AccessTokenVerifierService` (shared with `JwtStrategy`), with no separate CSRF check since the existing `SameSite=Lax` + no-CORS posture already rules out cross-origin handshakes. Sockets join a `household:<id>` room per-active-route (`joinHousehold`/`leaveHousehold`), not all at connect, since there's no global "current household" frontend state. Broadcasts carry a thin `{type, action, eventId, childId, householdId}` payload — clients refetch via React Query rather than the socket carrying full event bodies, and also refetch on every `connect`/reconnect as the reconnect strategy (no server-side replay log). See [ADR-0007](docs/adr/0007-websocket-realtime-sync.md).
- **Day-timeline & statistics** (also Phase 3, closing it out): a new read-only `EventModule` (`apps/backend/src/event/`) merges Feeding/Sleep/Diaper into one chronologically-sorted list (`GET .../events/daily`) and computes sleep hours/feeding count/`lastEventAt`-per-type (`GET .../events/stats`), reusing the existing per-type summary-mapping functions from `feeding.service.ts`/`sleep.service.ts`/`diaper.service.ts` rather than duplicating duration-derivation logic; `lastEventAt` is deliberately "most recent ever" per type, not scoped to the requested range. Both endpoints take `from`/`to` as full ISO-8601 instants — the frontend (`apps/frontend/src/lib/dayBoundaries.ts`) computes local-midnight-to-local-midnight boundaries itself from the browser's local `Date` semantics, so the backend does zero timezone reasoning. A new `GET /households/:householdId/members` endpoint (on the existing `HouseholdModule`) resolves user ids to emails for the frontend's `DailyTimeline` page (`apps/frontend/src/pages/DailyTimeline.tsx`), which also extends the real-time invalidation from ADR-0007 with one additional broad query-key invalidation so it stays live too.
- **Offline-first**: new entries are written locally first (e.g. IndexedDB) and shown optimistically; sync to the server happens when connectivity is available. Conflict resolution is last-write-wins based on the event's timestamp. Four of Phase 4's slices are implemented so far. First, "PWA basics" — an installable app shell via `vite-plugin-pwa`'s `generateSW` strategy (Web App Manifest + a service worker caching the built static assets, registered explicitly from `apps/frontend/src/main.tsx` rather than auto-injected), with `/api`/Socket.IO traffic deliberately left network-only (no offline data caching yet) — see [ADR-0008](docs/adr/0008-pwa-basics-via-vite-plugin-pwa.md). Second, local storage + optimistic UI for **new-entry creation** (Feeding/Sleep/Diaper Quick-Entry and Backfill-Create only, not edits/timer-stops): a shared `createEventOptimistically` engine (`apps/frontend/src/offline/`) writes to a generic IndexedDB `pendingEvents` store (via the `idb` package) *before* the network call, so the entry survives a failed/never-sent request; list/timeline components merge these pending records into the server query at render time and show a "saving"/"failed" badge for anything not yet confirmed. A failed create is deliberately kept visible (not rolled back) rather than following the standard optimistic-update rollback pattern — see [ADR-0009](docs/adr/0009-indexeddb-optimistic-create-engine.md). Third, a reconnect-triggered sync queue (`apps/frontend/src/offline/syncQueue.ts`, driven by `SyncQueueProvider`): on the browser's `online` event or the Socket.IO connection coming back up, every buffered `pending`/`failed` record (household/child-agnostic, not just the currently-mounted page's) is resent via the plain per-domain create call using its persisted original request body (`createInput` — the fix for ADR-0009's documented ghost-duplicate limitation, since a retry now reuses the same local record instead of creating a new one), with capped exponential backoff (max 6 attempts; 4xx failures aren't retried) and a self-rescheduling timer so a lone remaining failure keeps retrying autonomously — see [ADR-0010](docs/adr/0010-offline-sync-queue-reconnect-retry.md), including its accepted at-least-once (not exactly-once) delivery tradeoff. Fourth, offline-capable **edit + timer-stop** plus actual **Last-Write-Wins conflict resolution**: edits (PATCH) and timer-stops now buffer/optimistically-render/resync like creates (`updateEventOptimistically` + per-domain `update*EventOptimistic`/`stop*TimerOptimistic`, merged as an *overlay* on the matching server row rather than a new list entry), and LWW compares a submit-time `clientTimestamp` against a new server-side `Event.updatedAt` column (deliberately not the freely-editable `occurredAt`) — a losing buffered write is dropped and surfaced via an app-root, dismissible `ConflictNoticeBanner`. Note: Prisma 7 does *not* auto-bump `@updatedAt` on a nested detail-only `event.update()`, so the services set `updatedAt` explicitly (verified by a real-SQLite integration test) — see [ADR-0011](docs/adr/0011-offline-edit-stop-and-last-write-wins.md). Manual real-device installability verification (Android/iOS/Desktop) is the only remaining Phase 4 item; it can't be performed by an automated agent, so it's tracked as a deferred follow-up in `docs/known-issues.md` rather than blocking the phase.
- **Database**: Prisma ORM, SQLite for MVP, schema kept portable to PostgreSQL/MySQL via config-driven provider selection. Migrations via Prisma Migrate from the start.
- **Native wrapper**: a minimal wrapper around the React codebase is required even for the MVP, because push notifications are implemented per-platform through the wrapper (not Web Push). Phase 5 resolved the previously-open Capacitor-vs-Tauri question in favor of **Capacitor** (`appId: me.jkoschke.babytracker`, `webDir: dist`, config in `apps/frontend/capacitor.config.ts`) — the decisive criterion was push support: Capacitor has an official, Ionic-maintained `@capacitor/push-notifications` plugin with a documented FCM/APNs path, whereas Tauri still has no official mobile push plugin (upstream `tauri-apps/tauri#11651` still open as of this work), and Capacitor's Node/TS toolchain matches the team's skillset with zero Rust. The generated native project folders (`apps/frontend/android/`, `apps/frontend/ios/`) are committed (only their build outputs are gitignored), driven by `cap:sync`/`cap:android`/`cap:ios` npm scripts. Android is the primary build/install target; native builds are deliberately kept out of CI (no SDKs/signing on runners), and real-device build/install plus the Capacitor cookie/origin auth smoke test are tracked as deferred manual items in `docs/known-issues.md`. See [ADR-0012](docs/adr/0012-capacitor-native-wrapper.md), including its explicit FCM/APNs-as-unavoidable-cloud-relay exception to the self-hosted-only principle.
- **Package manager**: Bun (workspaces for the monorepo). **Runtime: Node.js**, deliberately not Bun — Bun-as-runtime compatibility with Prisma's query engine bindings and native Node modules (e.g. Argon2) wasn't considered stable enough at the time of this decision (Phase 0). Bun is build/install tooling only; Docker images and `nest start` run on Node.js. See PRD section 5.6.
- **Config file format**: YAML (see PRD 5.6).

## Roles & permissions model

Household membership carries a role that gates permissions (see PRD section 3):
- **Owner/Elternteil** — full read/write, can invite users, create/delete child profiles
- **Co-Parent** — full read/write on assigned child profiles
- **Betreuer** (later) — can log events only, no delete/manage
- **Beobachter** (later) — read-only

A user can belong to multiple households (e.g. separated parents), and a household can have multiple child profiles (siblings).
